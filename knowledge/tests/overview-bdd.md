# 振る舞い駆動開発（BDD）解説ガイド

## BDD とは

BDD（Behavior-Driven Development：振る舞い駆動開発）は、ソフトウェアの振る舞いを自然言語で記述し、それを基にテストを実装する開発手法です。ユーザーの視点から「何をするか」「どうなるか」を明確にし、開発チーム全体で共通理解を築くことを目的としています。

## BDD の特徴

### 1. 自然言語での記述

- プログラミング知識がない人でも理解できる平易な文章
- ビジネス要件を直接テストシナリオに反映
- ステークホルダー間での認識齟齬を防止

### 2. ユーザー視点での思考

- 機能の実装方法ではなく、ユーザーの体験に焦点
- 「なぜその機能が必要か」を明確化
- ビジネス価値の高い機能から優先的に開発

### 3. 継続的なコミュニケーション

- 開発者、テスター、ビジネス関係者の協働
- 要件の変更や追加に柔軟に対応
- ドキュメントとしても機能

## Gherkin 記法

BDD では Gherkin という構造化された言語を使用してシナリオを記述します。

### 基本構造

```gherkin
Feature: 機能の説明
  この機能が何を実現するかの概要

  Scenario: シナリオの説明
    Given 前提条件
    When 実行するアクション
    Then 期待される結果
```

### キーワードの役割

| キーワード   | 役割         | 説明                         |
| ------------ | ------------ | ---------------------------- |
| **Feature**  | 機能定義     | テストする機能全体の説明     |
| **Scenario** | シナリオ定義 | 個別のテストケースの説明     |
| **Given**    | 前提条件     | テスト開始時の状態や条件     |
| **When**     | アクション   | ユーザーが実行する操作       |
| **Then**     | 期待結果     | 操作後に期待される状態や結果 |
| **And**      | 追加条件     | 同じ種類のステップを追加     |
| **But**      | 否定条件     | 〜ではない条件を追加         |

### 記述例

```gherkin
Feature: ファイル説明機能
  ユーザーが選択したファイルについて AI が内容を説明する

  Scenario: Java ファイルの説明を要求する
    Given サンプルファイル A(`A.java`)が開かれている
    And ユーザーがファイルを選択している
    When ユーザーが「このファイルについて説明してください」と入力する
    Then AI がファイルの内容と構造について説明を返す
    And 説明にはクラス名とメソッドの概要が含まれる
```

## BDD のメリット

### 1. 要件の明確化

- あいまいな要件を具体的なシナリオに落とし込み
- 「何が完成か」の定義が明確
- 実装前に動作仕様を確定

### 2. コミュニケーションの改善

- 非技術者も理解できる記述
- チーム全体での認識統一
- 要件変更時の影響範囲の可視化

### 3. 品質の向上

- ユーザー視点でのテスト設計
- 網羅的なテストケースの作成
- 回帰テストの自動化

### 4. 保守性の向上

- 仕様書としても機能する生きたドキュメント
- 変更時の影響を事前に把握
- 新規参加者のキャッチアップが容易

## BDD の実践ポイント

### 1. シナリオ作成時の注意点

- **具体的に記述する**: 抽象的な表現を避け、具体的な値や状態を明記
- **ユーザー視点を保つ**: 内部実装ではなく、ユーザーが体験することを記述
- **独立性を保つ**: 各シナリオが他のシナリオに依存しないよう設計
- **読みやすさを重視**: 技術者以外も理解できる平易な表現を使用

### 2. 良いシナリオの例

```gherkin
Scenario: コードブロックをコピーする
  Given マークダウン形式のコードブロックが表示されている
  When ユーザーがコピーボタンをクリックする
  Then コードがクリップボードにコピーされる
  And 「コピーしました」のメッセージが表示される
```

### 3. 避けるべきシナリオの例

```gherkin
# 悪い例：実装詳細に依存
Scenario: API を呼び出す
  Given データベースにレコードが存在する
  When POST リクエストを送信する
  Then 200 ステータスが返される

# 良い例：ユーザー視点
Scenario: 新しいタスクを作成する
  Given ユーザーがタスク一覧画面を開いている
  When ユーザーが「新しいタスク」ボタンをクリックする
  Then タスク作成フォームが表示される
```

## まとめ

BDD は単なるテスト手法ではなく、チーム全体でソフトウェアの振る舞いを定義し、共通理解を築くためのコミュニケーション手法です。自然言語での記述により、技術者と非技術者の間の橋渡しを行い、より良いソフトウェア開発を実現します。

シナリオファイルを作成する際は、このガイドと併せて「シナリオファイルの書き方.md」も参照し、プロジェクト固有のルールと BDD の基本原則の両方を適用してください。
